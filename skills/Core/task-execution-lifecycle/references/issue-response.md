# Issue Response by Number

用于 `/hub issue <编号>`。目标是把问题池中的线索转换为可审计的真实现场、根因、止损结果和待审批修复包；不能把问题标题、截图或单次错误直接当作根因。

## Inputs

- 原样保留的编号文本，包括前导零。
- 当前项目身份，以及项目 helper 中登记的唯一问题源、编号字段和必要的表/视图范围。
- 问题记录中的相关页面、Thread、Run、Task、Tool Call、业务对象、时间、环境和附件线索。

项目、问题源或编号不能唯一确定时，只问一个最小澄清问题。没有登记问题源时先补项目 helper；不要把项目专属 URL、表 ID、字段或凭据写进 Agent Hub。

## Workflow

### 1. 精确受理

1. 以文本整值匹配编号，不做数值转换、前缀匹配或模糊搜索。
2. 匹配为零条或多条时停止，报告实际结果，不猜测记录。
3. 读取问题标题、描述、状态、时间、负责人、附件及关联链接；区分问题池原始内容与本轮新增判断。

### 2. 冻结现场并定位根因

1. 在项目文档工作区创建问题现场记录，保留观察时间、环境、复现入口、预期与实际、关联 ID、关键请求/响应或工具结果；凭据和无关个人信息脱敏。
2. 从会话起点而不是仅从报错 Run 开始取证：对照首条用户自然输入、客户端/协议附加的结构化信封、Runtime 接受的 `USER.ACTION` 和真正送入模型的规范化 USER message；附件名、Asset/Resource 身份及 URL 也要逐层对齐。
3. 沿真实链路核对页面或客户端表现、运行事件、请求与响应、服务日志、持久化数据和外部系统状态。按项目规则选择必要证据，不用静态代码或单个成功状态替代运行事实。
4. 明确分栏：`已验证事实`、`待验证假设`、`根因结论`。根因必须同时解释触发条件、症状、边界和为什么会出现当前错误表述；伴随缺陷与本次失败的直接原因必须分开。证据不足时继续安全的只读检查或明确阻塞。
5. 用反事实校验：移除所认定的原因后，原失败路径应不再产生同一失败；相邻不受影响路径不应被误伤。

### 3. 止损

优先执行最小、可回滚且不掩盖证据的措施，例如停止无效重试、隔离单一入口、保留已有产物、回退本轮临时变更或明确告知受影响范围。止损不得伪造成功、删除现场或绕开权限/契约。

以下情况必须先停在决策点：生产发布或服务启停、配置或权限调整、数据库/接口/契约变更、付费或不可逆调用、外部状态或消息写入、影响范围不明，或项目规则要求确认。记录止损动作、开始/结束时间、影响面、恢复条件和验证结果；无持续任务可停止时，也要明确“未重试/未扩大影响”的冻结状态。

### 4. 提交永久修复审批包

在实施前给出：

- 已确认根因及证据链。
- 最小修复点、owner、涉及仓库/模块和职责边界。
- 必须保持的既有行为与兼容性。
- 验证范围：原失败路径、反向用例、紧密关联回归和真实环境验收。
- 风险、回滚方式、配置/API/数据库/架构影响及项目要求的专项确认模板。
- 明确审批句：请用户回复同意实施或需要调整。

最初执行 `/hub issue` 不等于批准永久修复；只有用户在看到当前审批包后明确同意，才进入实现、测试、真实路径回归。审批也不自动授权 commit、push、PR、merge 或生产部署。

## Completion States

- `awaiting_approval`：现场、根因和止损已完成，永久修复包等待审批。这是本命令在审批前的正常终态。
- `blocked`：关键证据、身份、权限或唯一匹配缺失，已说明具体阻塞和当前可确认范围。
- `fixed`：已获审批，修复及约定验证全部完成；仍需披露未执行的部署或自然场景验收。

## Checklist

- 编号整值唯一匹配，前导零未丢失。
- 问题池内容与运行事实分开记录。
- 已核对首条用户原文、系统附加信封和规范化模型输入，未把系统注入内容归因给用户。
- 证据通过稳定 ID 对齐，事实、假设、结论清楚分离。
- 止损可回滚、未掩盖现场，并有验证结果。
- 修复前存在当前、明确、可追溯的审批。
- 最终回复给出记录路径、状态、根因、止损、审批方案和剩余边界。
