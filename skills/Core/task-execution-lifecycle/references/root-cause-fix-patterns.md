# Root-Cause Fix Patterns

用途：作为 `task-execution-lifecycle` 的按需参考；当用户说 `fix`、`fix <问题>` 或明确要求修复具体缺陷时读取。目标是先证明根因，再做最小修复，避免围绕症状叠补丁。

## Command Contract

`fix` 默认连续执行：

```text
reproduce -> locate -> analyze -> root-cause gate
-> propose -> implement -> regression verification
```

- 授权范围是目标问题内的诊断、必要测试和生产修复；不包含机会主义重构或相邻功能扩展。
- 方案形成后先简要说明根因、修改 owner、最小 diff 和验证方式；除非涉及新权限、高风险数据/接口动作或会改变用户目标，否则不等待额外确认，继续执行。
- `fix` 不自动包含 commit、push、PR 或 merge；这些动作由 `coding`、`pr` 或用户的单独授权触发。

## 1. Reproduce

1. 冻结 expected / actual、输入、环境、版本、入口、频率和最小验收信号。
2. 优先复现用户原始路径；难以直接运行时，可用最小失败测试、准确日志/trace、确定性静态反例或等价调用链作为复现证据。
3. 保存基线信号：失败输出、状态、截图、请求/响应、日志位置或具体断言。间歇性问题要记录触发条件和复现率。
4. 不能复现且没有等价证据时，状态只能是 `未复现`；继续做只读定位或增加可回收诊断，不把猜测写成根因，也不先改生产行为碰运气。安全证据源已查尽且缺失信息会改变判断时，再向用户请求最小必要上下文。

## 2. Locate

- 从真实入口沿数据、控制流和 owner 边界追到首个偏离预期的位置，不把最后抛错的位置自动当成根因。
- 同时检查输入、状态、配置、依赖、生成物、持久化、并发/时序、最近相关改动和运行环境；只读取会改变判断的证据。
- 用二分缩小、调用点搜索、最小探针、断点、日志或测试隔离边界。诊断性改动必须可识别、可回收，不能混成最终修复。
- 页面/API/runtime/tool 问题要区分入口、wiring、下游支持、业务结果和结果可见层，避免修错 owner。

## 3. Analyze With Independent Evidence

存在歧义时列出竞争假设；每个假设都要经过三种检查：

| Check | Question |
| --- | --- |
| 正向推理 | 如果该原因成立，还应观察到哪些结果、边界或失败？实际是否吻合？ |
| 逆向推理 | 要产生当前症状，哪些前置状态必须成立？证据能否从症状反向追到该状态？ |
| 交叉验证 | 代码路径、运行信号、测试、配置、历史变更或独立调用点中，是否至少有另一条不由同一结论推导出的证据？ |

- 主动寻找能推翻假设的反例，不只收集支持材料。
- 区分 trigger、root cause、contributing factor 和 symptom；最终方案应修 root cause，必要时再处理防护与可观测性。
- 多个失败可能同根因；共享状态、共享调用链或相同时序信号未排除前，不把它们并行当成独立 bug 修。
- 证据直接、机制唯一的机械缺陷可以走轻量路径，不强造多个假设；仍需一个决定性证据和一个边界/反例检查。

## 4. Root-Cause Gate

只有同时满足以下条件，才写“根因是”：

1. 能说明从触发条件到症状的完整因果机制。
2. 能解释为什么问题在当前条件出现、在相邻条件不出现。
3. 证据指向真实 owner，而不是只指向最后报错层。
4. 主要替代假设已被反证、降级或说明为何不成立。
5. 预期修复该原因会改变原始复现路径，且不会依赖 mock、fallback 或手工状态推进。

门禁未通过时，输出“当前最高置信假设 + 已有证据 + 缺失证据”，继续定位；不要进入生产修复。

## 5. Propose

方案至少说明：

- 要修改的真实 owner、文件/接口范围和不修改的相邻范围。
- 最小修复如何切断根因到症状的因果链。
- 备选方案及不采用原因；简单机械问题可只说明唯一方案。
- 回归测试如何在错误实现下失败、修复后通过，以及需要覆盖的正向、负向和边界 case。
- 接口、数据、权限、迁移、运行服务或跨仓库动作的风险与回滚/恢复方式。

## 6. Implement

- 沿现有架构和依赖方向修改根因 owner，保持最小 coherent diff、领域边界和公共 surface 稳定。
- 不用额外 fallback、兼容层、重试或异常吞噬掩盖未解决的根因，除非它本身是明确需求的一部分。
- 同步增加或修正能锁住根因的回归测试；期望值应独立于被测实现。
- 新证据推翻根因时立即停止叠补丁，回到 Analyze；清理本轮无效诊断或实现改动后再选方案。

## 7. Verify

按风险从窄到宽验证：

1. 原始复现路径由失败变为满足预期。
2. 回归测试有 red/green、临时回退或等价 falsifiability 证据，能证明它会抓住目标缺陷。
3. 相邻正向、负向和边界 case 未回归。
4. 必要的 lint、typecheck、build、项目测试、真实页面/API/workflow 或 quality orchestration 通过。
5. 最终 diff 只覆盖目标 owner，未遗留诊断代码、临时文件、mock/fallback 或架构污染。

如果根因属于无权修改的外部 owner，给出复现、根因证据、建议方案和阻塞点；不要在本地 owner 用症状补丁伪装修复完成。

## Completion Output

最终回复按实际复杂度裁剪，但要能回答：

- 如何复现，基线证据是什么。
- 根因是什么，正向、逆向和交叉验证证据如何闭合。
- 采用什么方案，为什么是最小根因修复。
- 修改了哪些 owner，哪些相邻范围保持不变。
- 原始路径、回归测试和扩展验证分别证明了什么。
- 哪些风险、环境或外部 owner 仍未验证。

完成声明同时遵守 `completion-evidence-patterns.md`；页面/Chat/MCP case 还需遵守 `case-execution-recovery.md`。
