# 监控—修复—自愈系统方法轮

## 1. 方法轮

```text
系统定位 -> 系统建模 -> 事实采集 -> 观察计算 -> 策略判断
   ^                                              |
   |                                              v
能力演进 <- 缺口复盘 <- 结果验证 <- 受控修复 <- 事件聚合
```

这不是一次性流水线。任何一轮都从系统目标和真实运行事实出发，以恢复结果和覆盖缺口回到下一轮建设。工具、组件和供应方只承接其中某个能力，不拥有整套方法。

## 2. 分层模型

| 层 | 回答的问题 | 典型内容 | 禁止混入 |
| --- | --- | --- | --- |
| Fact | 实际发生了什么 | start/end、状态转换、依赖调用、资源读数、动作回执 | 健康结论、告警级别 |
| Observation | 一段范围和时间内呈现什么状态 | rate、latency、open interval、absence、顺序冲突、趋势 | 通知渠道、修复副作用 |
| Policy | 什么状态值得采取什么响应 | SLO、窗口、阈值、基线、异常、抑制、路由 | 原始事实改写 |
| Incident | 哪些信号属于同一次影响 | 根事件、症状集、拓扑树、影响、证据、恢复状态 | 独立事实源 |
| Action | 如何减轻或消除影响 | runbook、重试、隔离、降级、回滚、扩缩容 | 未授权的无限自动化 |
| Verification | 是否真的恢复且没有扩大影响 | 后置条件、回归窗口、业务探针、回滚判定 | 仅以动作返回成功代替恢复 |

事实可以被重放，观察和策略可以演进，事件可以重新聚合；三者分离后，修改阈值或告警策略不要求业务系统重新发布。

## 3. 系统观测画像

每个接入系统维护自己的画像，通用方法不保存其具体值：

| 维度 | 最小内容 |
| --- | --- |
| Outcome | 关键用户旅程、成功/失败、SLO、可接受降级 |
| Topology | 系统、领域、服务、执行、节点、依赖、父子与调用关系 |
| Order | 期望节点顺序、允许并行/跳过/重入的条件 |
| Lifecycle | 阶段、进入/退出事实、终态、deadline、租约与回收语义 |
| Identity | 稳定实体 ID、correlation/root/parent ID；高基数 ID 只用于关联和下钻，不直接成为无界指标标签 |
| Ownership | 事实、策略、事件、通知、动作和验证的 owner |
| Authority | 可观察、可建议、需审批和可自动执行的边界 |

画像是系统特定配置或文档，不应复制成一套新的监控框架代码。

## 4. 覆盖矩阵

以关键旅程为单位展开，不用“已经有多少指标”衡量完成度：

```text
旅程 × 领域 × 拓扑节点 × 生命周期阶段 × 失败模式
     × 检测方式 × 策略 × 事件聚合 × 修复动作 × 验证证据
```

失败模式至少逐类检查：

- 显式失败：错误、拒绝、取消、panic、依赖失败。
- 未发生：未启动、未产生数据、未结束、心跳消失、消费者消失。
- 时序异常：卡住、超时、乱序、重复、并发冲突、父结束但子仍开放。
- 质量退化：延迟、错误率、吞吐、完整性或业务成功率恶化。
- 容量异常：积压、饱和、背压失效、资源持续增长、限额接近或耗尽。
- 恢复异常：重试耗尽、补偿失败、动作无效、恢复后复发、无法确认恢复。
- 观测异常：采集丢失、处理延迟、规则未执行、通知失败、恢复消息未送达。

每个矩阵单元只使用可验证状态，例如 `covered / partial / gap / N/A`，并附 evidence、owner 和下一步。`N/A` 必须写原因。

## 5. 事件与告警内容

告警是事件的投影视图，不是事实堆叠。至少包含四层：

1. **主干**：incident/root execution ID、父子执行树、当前受影响分支和根因候选。
2. **维度**：系统领域、拓扑节点、节点顺序、关键依赖和影响范围。
3. **策略**：命中的生命周期阶段、观察窗口、阈值/基线/SLO 来源、no-data 语义、聚合与抑制结果。
4. **处置**：诊断状态、建议或已执行动作、权限状态、验证进度、回滚/升级入口和恢复结论。

只有事实变化或策略重新计算不足以单独制造新事件。事件键、去重窗口、合并条件和恢复条件应稳定可解释；根因未知时明确标记 unknown，不把最早出现的症状伪装成根因。

## 6. 复用、适配、缺口和自建

先盘点现状，再做选择：

| 决策 | 进入条件 | 必须留下的证据 |
| --- | --- | --- |
| reuse | 已有能力满足目标、语义、可靠性、权限和成本边界 | 真实配置/运行结果、owner、限制 |
| adapt | 核心能力可用，只需薄适配即可进入统一事实或事件模型 | 适配契约、失败语义、维护 owner |
| gap | 当前不满足，但尚未达到建设时点 | 需求、影响、证据、临时处置、owner、复查时间/触发信号 |
| build-candidate | 缺口反复或影响关键目标，现有能力不可合理补齐 | consumer、边界、替代方案、全生命周期成本、安全与回滚评估 |
| N/A | 对当前旅程没有意义 | 影响面理由 |

自建前必须同时回答：

- 缺口是否影响关键旅程、SLO、恢复能力或跨系统重复成本。
- 现有能力为何不能通过配置或薄适配满足，而不是因为不熟悉就重建。
- 新组件的唯一 owner、真实 consumer、稳定契约和运维责任是什么。
- 采集、存储、计算、升级、权限、审计、容量、灾备和退役成本由谁承担。
- 如何逐步接入并可撤回，不让体系建设反向阻塞业务系统建设。

## 7. 自愈成熟度与动作门禁

| Level | 能力 | 适用边界 |
| --- | --- | --- |
| L0 感知 | 检测、聚合、触达、恢复通知 | 新场景默认从这里取得证据 |
| L1 辅助 | 给出诊断证据和可执行 runbook | 机制已知但动作仍需人工判断 |
| L2 审批执行 | 系统准备动作，授权后执行并验证 | 副作用可控但不宜无人值守 |
| L3 有界自愈 | 满足 guard 后自动执行、验证、回滚/升级 | 高频、机制稳定、幂等/可逆、影响半径和预算明确 |

自动动作必须有：明确 incident/action identity、前置条件、权限、幂等键或补偿、并发互斥、次数/时间/影响预算、完整回执、业务后置验证、失败回滚和人工接管。动作 API 返回成功只证明请求被接受，不证明系统已恢复。

## 8. 纵向切片验收

首个切片优先选择“影响大且当前不可感知”的关键旅程，贯通：

```text
真实故障注入或回放
  -> 事实可达且质量可判定
  -> observation/policy 正确识别显式失败或缺失
  -> incident 正确聚合拓扑、阶段和影响
  -> 目标渠道收到一次可行动通知
  -> 人工或自动动作遵守权限与预算
  -> 业务结果恢复并被独立验证
  -> 恢复消息触达，事件闭合，覆盖矩阵更新
```

验收至少报告检测时间、聚合正确性、动作结果、恢复确认、误报/漏报和未覆盖缺口。只看到指标、触发通知或动作返回成功，都不是闭环完成。

## 9. 常见反模式

- 为了“监控丰富”增加大量没有消费策略或修复路径的指标。
- 在业务代码中固化健康结论和告警阈值，使策略变化依赖重新发布。
- 每个症状单独告警，缺少根执行、父子树、阶段和影响聚合。
- 只监控错误记录，不监控没有开始、没有结束、卡住和数据断流。
- 因存在通用愿景而提前自建整套平台，尚无真实 consumer 和缺口证据。
- 因已有供应方能力而默认“已经覆盖”，没有真实配置与演练证据。
- 把自动重试称为自愈，却没有影响预算、后置验证、回滚或升级。
- 让 telemetry 写入、规则计算或通知失败阻塞主业务，且未显式要求这种同步安全门禁。
